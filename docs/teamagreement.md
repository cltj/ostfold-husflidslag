# 3. Arbeidsprinsipper

Vi skal:

* arbeide i små iterasjoner
* levere fungerende løsninger tidlig
* hente tilbakemeldinger tidlig og ofte
* gjøre antakelser eksplisitte
* teste usikre antakelser når det er praktisk mulig
* foretrekke enkle løsninger fremfor unødvendig kompleksitet
* behandle faglig uenighet som en naturlig del av utviklingsarbeidet
* endre arbeidsmåten når erfaring viser at noe ikke fungerer

⸻

# 4. Hvordan vi tar beslutninger

Ved viktige beslutninger spør vi:

1. Hvilke antakelser gjør vi?
2. Hva må være sant for at dette skal fungere?
3. Hva kan gå galt?
4. Hvordan kan vi teste eller validere dette?
5. Hva er det minste eksperimentet som kan gi oss nyttig informasjon?

Ved tekniske beslutninger vurderer vi ved behov et delsett av underliggende faktorer:

* kostnad
* reverserbarhet
* kompleksitet
* vedlikeholdbarhet
* skalerbarhet
* tidspress
* usikkerhet
* konsekvens dersom vi tar feil
* læringsverdi

Billige og lett reversible beslutninger: Ta beslutningen raskt.

Dyre, irreversible eller kritiske beslutninger: Undersøk grundigere før vi bestemmer oss.

# 5. Uenighet og konflikter

Når vi er uenige:

1. Beskriv tydelig hva vi faktisk er uenige om.
2. Skill mellom fakta, antakelser og preferanser.
3. Finn ut hvilken informasjon som kan avklare spørsmålet.
4. Gjennomfør et lite eksperiment når det er mulig.
5. Tidsbegrens diskusjonen ved behov.
6. Bruk teamets avtalte beslutningsregel dersom vi fortsatt ikke blir enige.

PS! Vi utfordrer ideer, ikke personer.

⸻

# 6. Definition of Done

En oppgave eller funksjon er ferdig når:

* Akseptansekriteriene er oppfylt.
* Koden er lagt i felles repository.
* Relevante automatiserte tester består.
* CI-kontrollene består.
* Koden er gjennomgått etter avtalt prosess.
* Nødvendig dokumentasjon er oppdatert.
* Funksjonaliteten kan demonstreres.
